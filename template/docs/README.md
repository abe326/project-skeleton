# {{PROJECT_NAME}} ドキュメント

`docs/` は **Git 管理対象で共有する前提**。秘密（URL・ID・パスワード・鍵）は書かない（`.claude/rules/secrets.md`）。

## 索引

| パス | 内容 | 更新の仕方 |
|:--|:--|:--|
| `プロジェクト概要.html` | 目的・思想・現在地（フェーズ・決めてほしいこと・次の節目・直近の決定）・将来対応・構成図と環境と設計書の入口・更新履歴。**人が最初に読む 1 枚** | `update-overview` スキル（決めてほしいこと・次の節目・直近の決定・タスクの状況は `build.py` が自動で書く） |
| `案件/` | 共有記録。タスク管理（作業の正本）・打合せ記録・確認依頼一覧 | `task` スキル、`.claude/rules/docs-management.md` |
| `案件/01_タスク管理/index.html` | タスクと画面の一覧 | `python3 docs/案件/01_タスク管理/build.py` |
| `設計書/` | 設計の正本。01〜09（何を・どう・誰と・なぜ・守る・確かめる・回す×2・耐える）＋ `decisions/`（ADR）＋ `runbook/`（手順）。索引と「いつ読むか」は `設計書/README.md` | `sync-design-docs` スキル（影響マップは `設計書/README.md` の「変えたもの → 一緒に直す正本」） |

運用ルール（置き場・秘密・作業領域）は `.claude/rules/` にある。設計書は「方針」、`.claude/rules/` は「日々のルール」と役割を分ける。

## フェーズ

フェーズは `立ち上げ` / `開発` / `運用` の 3 つ。正本は `プロジェクト概要.html` の「3. 現在地」（`data-phase`）で、生成直後は立ち上げ。
フェーズで仕組みの厳しさが変わる（立ち上げは拾って落とすだけ、設計書は未記入でよい）。止めるのは形と秘密だけで、どのフェーズでも空欄・未記入では止めない。
厳しさの表は文書に複製しない。`python3 .claude/hooks/phase.py --table` で見る。切り替えはユーザーが決め、`update-overview` スキルで行う。

## 推奨読書順

### 初めて触る人

1. `プロジェクト概要.html` — 目的・原則・いまどこにいるか
2. `設計書/01-overview.md` — 何を作っているか
3. `設計書/02-architecture.md` — どう作っているか
4. `設計書/04-設計原則.md` — なぜそうするか（迷ったときの基準）
5. `設計書/03-ステークホルダー.md` — 誰と決めるか（05〜09 は上の「作業種別 → 読む文書」で必要なときに）
6. `案件/01_タスク管理/index.html` — いま何が動いているか
7. `README.md`（ルート）— 動かし方

### 作業を再開する人（毎セッション）

1. SessionStart の注入（フェーズ・タスク件数・設計書の要確認と未記入・拾いもの）
2. `プロジェクト概要.html` の「3. 現在地」（決めてほしいこと・次の節目・直近の決定）
3. `案件情報.md`（ルート直下・Git 管理外）の実名の待ち・公開しない日程
4. 開発・運用フェーズで SessionStart が「設計書: 要確認 N 本」を出したら、着手する領域の設計書だけ先に読む

### 設計を変える人

1. `設計書/04-設計原則.md` — 原則に反していないか。反するなら §4 に変遷を書いてから
2. `設計書/decisions/README.md` — 既存の判断を確認
3. `設計書/decisions/ADR-000-テンプレート.md` — 新しい判断はこの型で
4. 変えたら `sync-design-docs` スキルで影響マップの文書を直す。決定は打合せ記録か課題の `## 決定` に書けば、`build.py` が概要 HTML の「直近の決定」に出す
