# docs/設計書/ — 設計の正本

プロダクトの設計・方針を示す恒久ドキュメント。**詳細仕様はコードが正本**で、設計書は概要・方針（基本設計レベル）にとどめる。スリムに保つ（1 本 80〜150 行、全体で 20 本以内）。
時点の状態（いまどこか・何が動いているか）は持たない。それは `docs/プロジェクト概要.html`・タスク md・`案件情報.md` の仕事。

## 変えたもの → 一緒に直す正本

**同じ作業の中で直す。** 表に無いものを変えたら、行を足すか「影響なし」を理由付きで報告する。どちらにも落とさずに進めない（`sync-design-docs` スキル）。1 列目のバッククォート内は変更パスの glob（複数は `・` 区切り）、2 列目のバッククォート内は直す文書（左から順に）。バッククォートで glob を囲んだ行は hook と `scripts/check_skeleton.py` が機械で読む。glob の無い行は人向け。

## 書き方

全設計書に共通。詳細は `.claude/rules/docs-management.md` の「設計書の書き方」。

- **冒頭**: `# NN タイトル — 一言` の直後に引用ブロック 3 行。1 行目は鮮度メタ（機械が読む。正確にこの形）: `> 最終更新: YYYY-MM-DD（<タスクID>: 要点）／ 対象: <追随するソースの glob を・区切り> / repo@<short-sha>`。ソースに依存しない文書は `対象: 案件情報.md §1・打合せ記録`（`repo@` 省略）。任意で末尾に ` ／ 鮮度: 90日`。雛形の初期値は `> 最終更新: {{CREATED}}（初版。雛形のまま）／ 対象: —`。2 行目 `> 作成: YYYY-MM-DD ／ 位置づけ: 〈何の正本か〉 ／ 対象読者: Claude Code・開発者`。3 行目 `> 扱わないもの: X → \`参照先\`、Y → \`参照先\``
- **§0 位置づけ** に固定文を置く: 「`未決`・`提案` の項目を根拠に『方針に反する』と指摘しない。`決定` に実装が反していれば実装側を直す（04 §3）」
- **表には「状態」列**を持つ。値は 決定 / 実装済 / 提案 / 未決。`実装済` は根拠パス必須
- **未決は本文に書かない。** 未決の正本は課題 md（`docs/案件/01_タスク管理/`、kind=課題。`new.py <area> "<問いの形>" --kind 課題`）。本文の決まっていない箇所には「（未決 QA-01）」のように**起票した課題の ID** を書く（起票前に ID を予想して書かない）。末尾の `## N. 未決` は固定文 1 行のまま書き足さない。本書に関わる未決の一覧は `python3 scripts/check_drops.py --refs NN`
- **末尾に `## 改訂履歴`**（表: 日付 / 内容 / 関連 ID。新しい順）。本文を変えたら同じ日に 1 行足し、鮮度メタの最終更新を合わせる
- **書かないもの**: タスク ID・SHA・進捗（「（未決 ID）」の参照・改訂履歴・鮮度メタ・04 §4 以外）、秘密の実値、実名。日付別・`_v2` ファイルは作らない（退避は `.work/_bk/`）
- **ID 体系**: P-（原則）、SH-（関係者ロール）、INV-（不変条件）、SCR-（画面。`docs/案件/01_タスク管理/screens/`）。未決は課題の ID（`areas.json` のプレフィックス。例 QA-01）で、設計書ごとの採番はしない
- **初期状態**: 各節は「空欄の表 or 箇条書き ＋ 括弧書きの例示 1 行」。例示は埋めたら消す
- **未記入の扱い**: 鮮度メタ行が雛形の初期値（`雛形のまま`）の文書は「未記入」と数える（情報。止めない）。節を 1 行でも埋めてメタ行を書き換えれば未記入でなくなる
- 実装と食い違ったら、まず設計書側で「どちらが正か」を確定してから下流を合わせる
