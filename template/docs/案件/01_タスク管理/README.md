# {{PROJECT_NAME}} タスク・課題・画面管理ツール

プロジェクトの未完了タスク・課題・画面の進捗を**ローカル Markdown ファイル＋ Python スクリプト**で管理する軽量ツールです。
Python は標準ライブラリのみで動きます（PyYAML 不要）。

> **分類（kind）**: 各エントリは `kind` で **タスク**（実行して完了させる作業）と
> **課題**（意思決定・すり合わせが必要な未決事項）に分類する。省略時はタスク扱い。
> 課題は「決着（意思決定が下りた）」時点で `close.py` でクローズし、実装が必要なら別途タスクを起票する。
> これにより「エピックの配下タスクは全部終わったが未決事項だけ残る」ケースで、未決事項を課題として
> 外出しし、エピックをクローズできる。
> **表示**: index.html では課題をタスクと同列に並べず、**リスト上部の専用バンド
> 「⚑ 課題（意思決定待ち）」（ピンク系の別背景色）に分離表示**する。課題は領域別/エピック別の
> タスクグループには現れない（検索・OPEN/CLOSED 切替はバンドにも同様に効く）。

## ディレクトリ構成

```
docs/案件/01_タスク管理/
├── open/           ← OPEN タスクの md（運用上の正本）
├── closed/         ← CLOSED タスクの md（クローズ済み）
├── screens/        ← 画面の md（SCR-NN_<名前>.md）
├── areas.json      ← 領域 → ID プレフィックスの対応表（プロジェクトで追記する）
├── build.py        ← open/ closed/ screens/ を走査して data.js を生成（概要 HTML のスナップショットも更新）
├── new.py          ← 新規タスク／課題の md 雛形を open/ に作成
├── close.py        ← タスクを open/ ↔ closed/ 間で移動
├── screen.py       ← 画面の作成（new）と status 更新（set）
├── data.js         ← 生成ファイル（index.html が読み込む）
├── index.html      ← 閲覧用 HTML（単一ファイル・外部依存なし）
└── README.md       ← 本ファイル
```

## タスクのクローズ基準（プロジェクトで書き換える）

コード変更を伴うタスクは、次の**3条件**が揃ったらクローズする（`close.py <ID>`）:

1. **対象環境へ適用済み** — 例: 開発環境へデプロイ済み
2. **確認者の確認が取れた** — 確認者はプロジェクトで定める
3. **正本へ反映済み** — 環境情報・設計書・台帳など、プロジェクトが正本と定めるものへ反映

- 確認は口頭アスクではなく、**環境に適用して実機で動作を見てもらう方式**を基本とし、確認待ちを理由に
  タスクを open のまま滞留させない。実機確認の見どころ・残論点は、クローズ時に本文へ記録するか後続タスクへ引き継ぐ
- コード変更を伴わないタスク（調査・ドキュメントのみ等）は条件 2 のみでクローズ可

> この節と `new.py` の本文テンプレート「完了条件（クローズ3条件）」は、プロジェクト開始時に
> 具体的な環境名・確認者・正本の名前に書き換える。

## 運用手順

### タスクを追加する

**方法 A: `new.py` を使う（推奨）**

```bash
# area とタイトルを指定
python3 new.py 横断 "ログイン画面のバリデーション追加"

# タイトルを後で書く場合は area のみ
python3 new.py 文書

# 課題（意思決定待ちの未決事項）として作成する場合
python3 new.py 運用 "バックアップ世代数の扱い" --kind 課題
```

`open/<ID>_<slug>.md` が作成され、`build.py` が自動で呼ばれて `data.js` が更新されます。
本文には 9 セクションの雛形（課題は 6 セクション）が入ります。

**方法 B: `open/` に md を直接作成した後 `build.py` を実行**

```bash
# open/<ID>_タイトル.md を手で作成し…
python3 build.py
```

### タスクをクローズする

```bash
python3 close.py QA-03
```

- `open/QA-03_*.md` を `closed/` へ移動
- `status: 完了`・`closed: <本日>`・`updated: <本日>` を自動書き換え
- 同じ ID prefix の付随資料（`QA-03_内容_YYYYMMDD.md` / `.png` / `.html` 等）も一緒に移動
- `build.py` が自動実行されて `data.js` 更新

### タスクを再オープンする

```bash
python3 close.py --reopen QA-03
```

- `closed/QA-03_*.md` を `open/` へ移動（付随資料も随伴）
- `status: 未着手`・`closed: （空）`・`updated: <本日>` に書き換え

### 画面を追加・更新する

```bash
# 採番して作成（screens/SCR-01_ログイン.md）
python3 screen.py new "ログイン" --path /login --owner 担当者

# status を更新（未着手 / 実装中 / 確認待ち / 完了 / 保留）
python3 screen.py set SCR-01 実装中
```

どちらも実行後に `build.py` が呼ばれて `data.js` が更新されます。

### data.js を再生成する

```bash
python3 build.py
```

`open/`・`closed/`・`screens/` を走査して `data.js` を上書きします。バリデーション警告（ID 重複・必須欄欠落・許可値外・未知の画面 ID 参照）は標準エラーに表示されますが、処理は継続します。

### 検証だけ行う（`--check`）

```bash
python3 build.py --check
```

`data.js` も概要 HTML も書かずに検証だけ行います。警告が 0 件なら終了コード 0、1 件以上なら 1 を返すので、
コミット前チェックや CI に組み込めます。

### 閲覧する

`index.html` をブラウザで開くと `data.js` を読み込んでタスク一覧が表示されます。ツールバー左端の「タスク / 画面」で
ビューを切り替えます。

> **注意**: 静的 HTML 単体ではファイルへの書き込みができません。クローズ等の書き込み操作は `close.py` などの CLI 経由で行ってください。

## md ファイルのスキーマ（タスク）

各ファイルは先頭にフロントマターを持ちます。

```markdown
---
id: QA-03
title: ログイン画面のバリデーション追加
area: 横断
kind: タスク
status: 未着手
priority: 高
epic:
owner:
tags: [0527]
screens: [SCR-01]
source:
created: 2026-06-28
updated: 2026-06-28
closed:
---

（ここから下が Markdown 本文）
```

### フロントマター各項目

| フィールド | 必須 | 説明 | 許可値 / 形式 |
|-----------|:----:|------|--------------|
| `id`      | ✅   | タスク ID（プレフィックス-連番） | `QA-01`、`DOC-03` など |
| `title`   | ✅   | タスクのタイトル | 自由文字列 |
| `area`    | ✅   | 担当領域 | 下表「領域プレフィックス対応表」参照 |
| `kind`    | —   | 分類（省略時は `タスク`） | `タスク` / `課題`（課題＝意思決定待ちの未決事項。決着でクローズ） |
| `status`  | ✅   | 進行状態 | `未着手` / `進行中` / `方針確定` / `確認待ち` / `保留` / `完了` |
| `priority`| ✅   | 優先度 | `最高` / `高` / `中` / `低` |
| `epic`    | —   | 大きな括り（エピック） | 自由文字列（省略可）。`<PREFIX>-00` の ID を持つタスクがエピック親 |
| `owner`   | —   | 担当者名 | 自由文字列（省略可） |
| `tags`    | —   | タグ（複数可） | `[0527, 0618]` 形式、空は `[]` |
| `screens` | —   | 関連する画面 ID（複数可） | `[SCR-01, SCR-02]` 形式、空は `[]`。省略可 |
| `source`  | —   | 元ネタファイル名 | 自由文字列（省略可） |
| `created` | —   | 作成日 | `YYYY-MM-DD` |
| `updated` | —   | 最終更新日 | `YYYY-MM-DD` |
| `closed`  | —   | クローズ日（OPEN タスクは空） | `YYYY-MM-DD` または空 |

> `state`（`"open"` / `"closed"`）は `data.js` 生成時にフォルダ名から自動付与されます。md には書きません。

### 付随資料の併置

タスク本体と同じフォルダに `<ID>_内容_YYYYMMDD.md` / `.png` / `.html` のような付随資料を置けます。
フロントマターに `id` を持たない md は `build.py` がタスクとして扱いません。`close.py` はこれらを本体と一緒に移動します。

## md 本文のテンプレート（9 セクション）

フロントマター以降の本文は、次の **9 セクション構成**で書く。狙いは「タスクを開いた瞬間に "何をするか" が分かる」こと。背景・現状・経緯を上位に置くと用件が埋もれるため、**用件（概要・意義・変更点・計画）を上に、背景（経緯・参照）を下に**並べる。該当の無いセクションは「なし」と書くか省略してよい。`new.py` がこの雛形を本文に書き出す。

```markdown
## 概要
（このタスクで何をするか。1〜3行で用件だけ）

## 対応の意義（なぜやるか）
- 対応しないデメリット: …
- 対応するメリット: …
（＝優先度の根拠。ここで「やる価値」を示す）

## 対応後の変更点（利用者視点）
（利用者から見た UI/UX の変化。純粋なバックグラウンド処理のみなら「なし」）

## 対応計画の概要
- 作業項目を箇条書き（スキャンできる粒度）

## 対応計画の詳細
（各作業項目の具体。対象ファイル・データモデル・移行方針・技術判断）

## 影響・依存
（他タスク・画面・設計書・レビュー観点との関係）

## 完了条件（クローズ3条件）
1. 対象環境へ適用済み
2. 確認者（プロジェクトで定める）の確認
3. 正本（環境情報・設計書・台帳等）への反映
（コード変更を伴わないタスクは条件2のみでクローズ可。その旨を明記する）

## 過去の経緯
（これまでの打合せ・決定の変遷。「なぜ今この結論か」）

## 参照情報
（打合せ出典・設計書・関連コミット・関連タスク ID・関連画面 ID）
```

- **「完了条件」はプロジェクトで書き換える**: `new.py` の `TASK_BODY` と本 README の「クローズ基準」を、環境名・確認者・正本の実名に置き換える
- **経緯の扱い**: 打合せの生発言・時刻などは「過去の経緯」または「参照情報」へ。概要・計画セクションに混ぜない
- 課題（`--kind 課題`）の雛形は「概要 / 論点 / 決定候補 / 決着条件 / 過去の経緯 / 参照情報」の 6 セクション

## 領域プレフィックス対応表（`areas.json`）

`new.py` は同じフォルダの `areas.json` を読んで ID のプレフィックスを決めます。

```json
{
  "areas": {
    "横断": "QA",
    "文書": "DOC",
    "環境": "ENV",
    "運用": "OPS"
  }
}
```

| area（フロントマター値） | プレフィックス |
|------------------------|:-------------:|
| 横断                   | `QA`          |
| 文書                   | `DOC`         |
| 環境                   | `ENV`         |
| 運用                   | `OPS`         |
| 上記以外               | 先頭3文字大文字（自動） |

- **プロジェクト固有の領域は `areas.json` に追記する**（例: `"認証": "AUTH"`）。`new.py` の書き換えは不要
- 未登録の area で起票すると先頭 3 文字を大文字化したプレフィックスで自動採番される。意図した ID にしたい場合は先に `areas.json` へ追加する
- `areas.json` が無い／壊れている場合は警告を出して自動採番のみで続行する

## 画面（screens/）

画面ごとの実装状況を `screens/SCR-NN_<名前>.md` で管理し、タスクと相互に紐付けます。

### スキーマ

```markdown
---
id: SCR-01
name: ログイン
path: /login
status: 未着手
owner:
tags: []
created: 2026-06-28
updated: 2026-06-28
---

## 概要
（この画面の役割。誰が・何のために使うか）

## 主要な操作
- …

## 参照（設計書・タスク）
- 設計書:
- 関連タスク: タスク側の frontmatter `screens:` にこの ID を書くと build.py が逆引きする
```

| フィールド | 必須 | 説明 | 許可値 / 形式 |
|-----------|:----:|------|--------------|
| `id`      | ✅   | 画面 ID | `SCR-NN`（`screen.py new` が採番） |
| `name`    | ✅   | 画面名 | 自由文字列 |
| `path`    | —   | URL パスや画面識別子 | 自由文字列（省略可） |
| `status`  | ✅   | 実装状況 | `未着手` / `実装中` / `確認待ち` / `完了` / `保留` |
| `owner`   | —   | 担当者名 | 自由文字列（省略可） |
| `tags`    | —   | タグ | `[a, b]` 形式、空は `[]` |
| `created` / `updated` | — | 作成日 / 最終更新日 | `YYYY-MM-DD` |

### screen.py

```bash
python3 screen.py new "<名前>" [--path /x] [--owner 名前]   # 採番して作成 → build.py
python3 screen.py set <ID> <status>                          # status / updated を更新 → build.py
```

フロントマターの書き換えは `close.py` のユーティリティ（`find_md` / `rewrite_md`）を import して使っているため、
`screen.py` は `close.py` と同じフォルダに置く必要があります。

### タスクとの関連付け

- タスク側の frontmatter に `screens: [SCR-01, SCR-02]` を書く（画面側にはタスク ID を書かない）
- `build.py` がタスクの `screens:` を逆引きして、各画面の `tasks` を計算する
- 存在しない画面 ID を参照すると `build.py` が警告する（`--check` では終了コード 1）
- index.html では、タスク詳細の「画面」チップをクリックすると画面ビューのその画面へ、画面詳細の「関連タスク」を
  クリックするとタスクビューのそのタスクへ移動する（CLOSED タスクは打消し線で表示。OPEN/CLOSED フィルタで
  隠れる場合は自動で「すべて」に切り替わる）

## プロジェクト概要 HTML との連動（スナップショット）

`build.py` は `docs/プロジェクト概要.html`（このフォルダから見て `../../プロジェクト概要.html`）が存在し、
中に次のマーカー対があれば、その**内側だけ**を置き換えて書き戻します。

```html
<!-- BEGIN:task-snapshot -->
（ここが build.py のたびに差し替わる）
<!-- END:task-snapshot -->
```

埋め込む内容（`<p>` と `<table>` のみ・外部依存なし）:

- 生成時刻、OPEN / CLOSED 件数、OPEN のうち課題・確認待ち・進行中の件数
- 最高優先の OPEN 上位 10 件（ID・タイトル・優先度・状態）
- 画面の進捗（完了 n / 全 m）

ファイルやマーカーが無い場合は注記を出して続行します（`--check` の警告数には数えません）。
`--check` では書き込みません。

## data.js の仕様（index.html との契約）

`build.py` が生成する `data.js` の形式:

```js
window.TASKS = [
  {
    "id": "QA-03",
    "title": "ログイン画面のバリデーション追加",
    "area": "横断",
    "status": "未着手",
    "priority": "高",
    "kind": "タスク",
    "epic": "",
    "owner": "",
    "tags": ["0527"],
    "screens": ["SCR-01"],
    "source": "",
    "created": "2026-06-28",
    "updated": "2026-06-28",
    "closed": "",
    "state": "open",
    "body": "## 概要\n..."
  }
];
window.SCREENS = [
  {
    "id": "SCR-01",
    "name": "ログイン",
    "path": "/login",
    "status": "実装中",
    "owner": "",
    "tags": [],
    "created": "2026-06-28",
    "updated": "2026-06-28",
    "state": "screen",
    "body": "## 概要\n...",
    "tasks": [
      { "id": "QA-03", "title": "ログイン画面のバリデーション追加", "state": "open", "status": "未着手", "kind": "タスク" }
    ]
  }
];
```

- `state`: タスクは `"open"` または `"closed"`（フォルダ由来）、画面は `"screen"`。md には書かない
- `body`: フロントマター以降の生 Markdown 文字列
- `SCREENS[].tasks`: タスクの `screens:` からの逆引き（`build.py` が計算）
- ソート順: プレフィックス昇順 → 連番昇順（安定ソート）
- 日本語はそのまま（`ensure_ascii=False`）
- コミット時の初期値は `window.TASKS = []; window.SCREENS = [];`。`index.html` は `window.SCREENS` が未定義でも動く
