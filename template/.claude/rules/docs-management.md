# ドキュメント管理ルール

## docs/ の構成

この構成図が正本。`docs/README.md`・`CLAUDE.md` §4 は要約。

```
docs/
├── README.md                 ← 索引・作業種別 → 読む文書・推奨読書順
├── プロジェクト概要.html       ← 目的・思想・現在地・将来対応・構成図と設計書の入口（update-overview スキルで更新）
├── 案件/                     ← 共有記録（Git 管理対象）
│   ├── README.md
│   ├── 01_タスク管理/         ← 作業と未決の正本（タスク md・課題 md ＋ new.py / close.py / screen.py / build.py）
│   │   ├── README.md / 詳細仕様.md ← 1 画面の要約 / スキーマ・雛形・data.js の契約
│   │   ├── open/  closed/    ←   <ID>_タイトル.md（課題は kind: 課題）
│   │   └── index.html / data.js / areas.json / screens/
│   ├── 02_打合せ/             ← 打合せ記録（YYYYMMDD_タイトル.md。決定・未決・宿題の各行に落ち先）
│   └── 確認依頼一覧.md         ← 相手に確認・判断してほしいことの一覧（各行に課題かタスクの ID）
└── 設計書/                   ← 設計の正本（索引・影響マップ・書き方は README.md）
    ├── 01-overview.md        ← 何を作るか
    ├── 02-architecture.md    ← どう作るか（データの流れと信頼境界）
    ├── 03-ステークホルダー.md  ← 誰と決めるか（ロール SH-xx・判断権限・確認の取り方・NG）
    ├── 04-設計原則.md         ← なぜそうするか（原則 P-xx・緊張関係・方針の変遷）
    ├── 05-セキュリティ設計.md  ← 何を守るか（境界・認証権限・格付け・鍵・インシデント）
    ├── 06-品質設計.md         ← 何を壊れたとみなすか（重大度・機械のゲート・レビュー観点・不変条件 INV-xx・テスト）
    ├── 07-開発運用設計.md      ← どう回すか・開発側（環境・ブランチ・DB・デプロイ・戻し・監視）
    ├── 08-利用者運用設計.md    ← どう回すか・利用者側（業務フロー・権限付与・サポート・障害時の文面）
    ├── 09-非機能と縮退.md      ← どこまで耐えるか（目標・容量・バックアップ・縮退・監視条件・費用）
    ├── decisions/            ← ADR（1 判断 1 ファイル。索引は README.md、型は ADR-000-テンプレート.md）
    └── runbook/              ← 手順（1 操作 1 ファイル。型と索引は README.md）
```

- docs/ の外で同じ扱いのもの: `.claude/ハーネス台帳.md`（ハーネスの候補と定義済みの台帳。ID `HN-NN`。`harness` スキル）
- `docs/` は **Git 管理対象で共有する前提**。秘密（URL・ID・パスワード・鍵）は書かない（`.claude/rules/secrets.md`）。実値の正本は `環境情報.md`、関係者・日程は `案件情報.md`（どちらもルート直下・Git 管理外）
- 作業単位は **タスク**（`01_タスク管理/` の md）。起票・クローズは `task` スキル（`docs/案件/01_タスク管理/README.md`）

## 資料の配置先

| 種別 | 配置先 |
|------|--------|
| 作業の経緯・設計判断・検討記録 | 該当タスク md（`01_タスク管理/open/`・`closed/` の `<ID>_*.md`）本文へ追記 |
| タスクに付随する成果物（提出資料・サンプル・スクショ等で残す価値のあるもの） | タスク md と同じフォルダに `<ID>_内容_YYYYMMDD.拡張子` で併置（例: `UI-01_画面スクショ_20260101.png`） |
| 打合せの要約・文字起こし | `02_打合せ/YYYYMMDD_タイトル.md`（決定・未決・宿題の各行に落ち先。書き方は `02_打合せ/README.md`） |
| 決まっていないこと（未決） | 課題 md（`new.py <area> "<問いの形>" --kind 課題`）。**未決の正本はここだけ**。設計書本文からは「（未決 QA-01）」で参照 |
| 相手に確認・判断してほしいこと | `確認依頼一覧.md`（各行に課題かタスクの ID。片付いたら `[x]` にして履歴節へ） |
| ハーネスの候補（今後・毎回・二度と…と言われたこと） | `.claude/ハーネス台帳.md` に状態「候補」で 1 行（`harness` スキル。定義はユーザーの承認後） |
| 横断的に参照される設計判断（昇格） | `docs/設計書/decisions/ADR-NNN-<短い英語>.md`（`ADR-000-テンプレート.md` の型） |
| 恒久的な仕様・方針 | `docs/設計書/`（詳細はコードが正本。設計書は概要・方針） |
| 恒久的な方針（セキュリティ・品質・運用） | `docs/設計書/03〜09`（何を・どう＝01・02、誰と＝03、なぜ＝04、守る＝05、確かめる＝06、回す＝07・08、耐える＝09） |
| 手で行う操作の手順 | `docs/設計書/runbook/<操作名>.md`（`runbook/README.md` の型。値は書かず `環境情報.md` §n 参照） |
| タスク md から参照する証跡（大きい・機密・生データ） | `.work/証跡/<タスクID>_内容/`（`.claude/rules/work-area.md`） |
| 受領した一次資料そのもの | `.work/機密/<タスクID>_内容/`（同上） |
| 使い捨ての中間生成物 | `.work/一時/YYYYMMDD_用途/`（`scratch` スキル） |

どのタスクにも紐づかない大きな資料の置き場に迷う場合は、勝手に新フォルダを作らず**ユーザーに確認する**（番号付きカテゴリの新設はユーザー判断）。

## 設計書と ADR

- `docs/設計書/` は**正本**。実装と食い違ったら、まず設計書側で「どちらが正か」を確定してから下流を合わせる
- タスク md に書いた判断のうち、**複数タスク・複数領域に効くもの**は ADR へ昇格する。ADR は 1 判断 1 ファイル、節は Status / Context / Decision / 却下した案 / Consequences / 関連
- ADR を足したら `decisions/README.md` の索引を同じ作業で更新する。概要 HTML の「直近の決定」は `build.py` が打合せ記録の決定行と閉じた課題の `## 決定` から作る（手で書かない）。関係者に見せたい決定は、打合せ記録に無ければ課題を `new.py … --decided "<決定>" --to "反映済: ADR-003"` で起票してすぐ閉じる

## 設計書の書き方（docs/設計書/ 共通）

- **冒頭 3 行**: `# NN タイトル — 一言` の直後に引用ブロック 3 行。**1 行目は鮮度メタで、`scripts/docs_freshness.py` と `scripts/check_skeleton.py` が読む。正確にこの形**:
  `> 最終更新: YYYY-MM-DD（<タスクID>: 要点）／ 対象: <追随するソースの glob を・区切り> / repo@<short-sha>`
  ソースに依存しない文書は `対象: 案件情報.md §1・打合せ記録`（`repo@` 省略）。任意で末尾に ` ／ 鮮度: 90日`。雛形の初期値は `> 最終更新: {{CREATED}}（初版。雛形のまま）／ 対象: —`。2 行目は `> 作成: … ／ 位置づけ: … ／ 対象読者: …`、3 行目は `> 扱わないもの: X → \`参照先\``
- **事実・決定・未決を書き分ける**。表には「状態」列（決定 / 実装済 / 提案 / 未決。`実装済` は根拠パス必須）。**未決は本文に書かず**、課題 md（kind=課題）に起票して、本文の決まっていない箇所から「（未決 QA-01）」で参照する（ID は起票してから写す）。末尾の `## N. 未決` は固定文 1 行のまま書き足さない。**`未決`・`提案` を根拠に「方針に反する」と指摘しない**。`決定` に実装が反していれば実装側を直す
- **改訂履歴は必須**。本文を変えたら同じ日に末尾 `## 改訂履歴` に 1 行足し、鮮度メタの最終更新を合わせる。タスク ID・SHA・進捗は「（未決 ID）」の参照・改訂履歴・鮮度メタ・04 §4 以外に書かない
- **日付別・`_v2` ファイルを作らない**。上書きする。退避が要るなら `.work/_bk/`
- **影響マップ**（`docs/設計書/README.md` の `## 変えたもの → 一緒に直す正本` 直後の表）: 1 列目のバッククォート内が変更パスの glob（`・` 区切り）、2 列目のバッククォート内が直す文書。**バッククォート内を hook と検査が機械で読む**。glob の無い行は人向け。行を足したら `python3 scripts/check_skeleton.py` で実在を確かめる
- **棚卸し**（設計書と実装の突き合わせ）: 見直しリストは `docs/案件/01_タスク管理/open/<DOC-ID>_見直しリスト_YYYYMMDD.md`、中間物は `.work/証跡/<DOC-ID>_棚卸_YYYYMMDD/`。設計書本体には結果（決定・未決）だけを反映する
- **ID 体系**: P-（原則。04）、SH-（関係者ロール。03）、INV-（不変条件。06 §6）、SCR-（画面）、HN-（ハーネス。`.claude/ハーネス台帳.md`）。未決は課題の ID（`areas.json` のプレフィックス。例 QA-01）。旧 U-xx は使わない（`scripts/check_drops.py` が情報で出す）

## 命名規則

- **タスク md**: `<ID>_タイトル.md`（ID は領域プレフィックス＋連番。領域は `01_タスク管理/areas.json`）
- **タスク付随資料**: `<ID>_内容_YYYYMMDD.拡張子`
- **打合せ**: `YYYYMMDD_タイトル.md`（決定・未決・宿題の各行に落ち先）
- **ADR**: `ADR-NNN-<短い英語>.md`
- **日本語 OK**: フォルダ名・ファイル名ともに日本語使用可

## アーカイブ

過去の記録をアーカイブ用フォルダ（`_アーカイブ/` 等）へ凍結したら、**そこへ新しいファイルを追加しない**。参照は自由。
