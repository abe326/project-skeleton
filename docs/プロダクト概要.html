project-skeleton

AI と仕事を始める初日から、置き場・記録・仕組みが揃っている。

開発でも、PM でも、運用保守でも、インフラや SaaS の管理でも、同じ一式を使います。業務ごとに型を選び分ける必要はありません。タスク管理・最低限の記録・AI への指示（ハーネス）を最初から置いておき、使いながら自分たちのやり方に合わせて直していく。AI 導入の初動を早くするための起爆剤です。

# Claude Code に「○○のプロジェクトを作って」と頼むと、new-project skill がこれを実行する $ python3 scripts/init.py 新案件 --name "新案件" --slug new-case → タスク一覧の初期化 → git init + 初回コミット → 構成の検査まで一気に通す # 既存のフォルダには --merge。足りないファイルだけを足し、既存には触れない
解決する課題

AI を入れても、仕事の型が整うまでに時間がかかる

AI を業務に入れるとき、最初につまずくのは AI の性能より、周りの整え方です。

何から整えるか決まらないタスクの置き場、記録の残し方、AI への指示。毎回ゼロから考え、手が止まる。
会話が流れて残らないAI とのやり取りで決まったことが、チャットに埋もれて翌日には探せない。
AI への指示が育たない同じ注意を何度も繰り返し、人ごとに指示がばらつく。うまくいったやり方が仕組みにならない。
3 つの起爆剤

最初に置いてあるのは、どの仕事にも要る 3 つ

機械は hook・スクリプト・検査で自動的に効くもの、手順は Claude Code が skill として読んで実行するものです。

01

タスク管理

Markdown 1 枚が 1 件。作業（タスク）と、まだ決まっていないこと（課題）を同じ置き場で持ち、一覧は HTML で切り替えて見ます。起票も完了も Claude Code に頼めば済みます。

手順task　機械new.py・close.py・build.py

02

最低限の記録

打合せや作業の区切りで出た「決まったこと・決まっていないこと・あとでやること」を Claude が拾い、置き場へ落とします。落ちていないものがあるときだけ、ターンの終わりに 1 回拾い直させます。セッションの始めには現在地を自動で渡します。

手順pickup　機械pickup_check・session_context

03

ハーネス設計

同じ手順を 2 回した、「それはしないで」と言われた。そうした場面を Claude が候補として台帳に書き、承認されたものだけを skill・hook・ルールとして定義します。AI への指示が、仕事をしながら育ちます。

手順harness　機械check_harness

使う場面

業務を選ばない。効くところが違うだけ

型を選び分ける必要はありません。同じ一式を置き、その仕事で要るところから使います。下は例です。

場面よく効くところ
開発タスクと課題の管理、変更に合わせた設計書の追随、テストや hook の整備
PM 業務打合せ記録と落ち先、「決めてほしいこと」と期日の一覧、関係者と判断権限の整理
運用保守定常作業と追加開発をタスクで一緒に持つ。手順は runbook に残し、同じ手順の 2 回目はハーネスの候補にする
インフラ・SaaS の管理環境の実値を Git 管理外の環境情報に集める。設定変更の経緯を記録に残し、してはいけない操作は許可設定で止める
強制しない、育てる

決まりは初期値。合わなければ変えてよい

ここにある決まりは、よくある失敗を防ぐための出発点で、使い方を押しつけるためのものではありません。自分たちの方針に合わなければ変えられますし、変え方もこの中に用意してあります。

機械が止めたり、やり直しを促したりするのは 3 つだけ。秘密を共有物に書いたとき、決めた置き場の外にファイルを作ったとき、拾ったものがどこにも落ちていないとき。空欄・未記入・未決の多さでは止めません。直す文書の候補や鮮度は、知らせるだけです。
厳しさを変えるフェーズ（立ち上げ・開発・運用）で hook と検査の厳しさが変わる。立ち上げ期は拾うだけ。
置き場を合わせる既存の仕組みが使う決まった場所は .claude/project.json に書けば、ガードが通す。コードは書き換えない。
仕組みを足す・外すharness スキルで候補を台帳に書き、承認して定義する。拾い直しの hook は CLAUDE_PICKUP=off で止められる。
文書は使う分だけ設計書のひな形は空のままでよい。未記入は数えて知らせるだけで、止めない。
既存のフォルダにも--merge は足りないファイルだけを足し、既存には触れない。違いは一覧で見せる。
マシンの設定と分ける案件で揃う範囲（CLAUDE.md・.claude/）と、マシンの設定に左右されるものを分けて表示する。
1 日の流れ

いつ、何が働くか

機械(hook・スクリプト)手順(skill)
セッション開始

現在地を受け取る

  • session_contextフェーズ・open のタスク・文書の要確認・拾いもの・マシン側の混入を 8 行以内で渡す
  • CLAUDE.md作業の種類に応じて読む文書を絞る
作業の前

置き場を決める

  • work-placement紐づくタスクを決めてから手を動かす
  • scratch一時的な出力は日付のフォルダへ
  • work_area_guard決めた置き場の外への書き込みは、書く前に止める
作業の区切り

拾って落とす

  • pickup決まったこと・未決・あとでやることを、反映済・タスク・課題のどれかへ
  • pickup_check落ち先の無いものがあれば、1 回だけ拾い直させる
  • design_docs_reminderファイルを変えたら、一緒に直す文書の候補を示す
節目

まとめて点検する

  • audit-design-docs記録・タスク・実物と突き合わせて見直しリストを作る
  • docs_freshness / check_drops文書の鮮度と、落ち先の無い行を一覧にする
生成されるもの

作業フォルダの中身

CLAUDE.md ＋ .claude/rules

守ること・セッション開始時の手順・読む文書の表。rules は作業領域・文書管理・秘密の 3 本。

.claude/skills（9 本）

work-placement ／ scratch ／ task ／ pickup ／ harness ／ update-overview ／ update-env-info ／ sync-design-docs ／ audit-design-docs

.claude/hooks（5 本）

開始時の現在地、置き場のガード、変更時の文書の候補、依頼文の手がかりの記録、区切りでの拾い直し。テスト付き。

docs/案件/

タスクと課題（1 件 1 枚と一覧 HTML）、打合せ記録、相手に確認したいことの一覧。

docs/プロジェクト概要.html

目的・思想・現在地・これからの 1 枚資料。タスクの件数や決めてほしいことは自動で反映。

docs/ハーネス台帳.md

AI への指示の候補と、承認して定義したものの一覧。

docs/設計書

01〜09 の文書のひな形と、判断の記録（decisions）・手順書（runbook）。使う分だけ書けばよい。

.work/ ・ 環境情報.md

Git 管理外。作業領域（証跡・機密・一時・退避）と、URL・アカウントなど実値の正本。

scripts/ ・ .claude/project.json

構成・落ち先・文書の鮮度の検査。案件ごとの違い（決まった置き場・入れ子のリポ）は project.json に書く。

文書のひな形

9 本を用意し、使う分だけ書く

どれを書くかは仕事しだいです。空のままでも検査は止めません。作業の種類ごとに読む文書は CLAUDE.md の表で絞ります。

#文書何の正本か
01overview目的・範囲・成功条件・用語
02architecture構成・データの流れと信頼境界・環境
03ステークホルダー関係者のロール・判断権限・確認の取り方
04設計原則原則・迷ったときの決め方・方針の変遷
05セキュリティ設計守る対象・権限・データの格付け・してはいけない操作
06品質設計何を壊れたとみなすか・機械が見ているもの・テスト
07開発運用設計変更の流れ・反映・戻し
08利用者運用設計業務フロー・権限の付与と剥奪・障害時の文面
09非機能と縮退目標・容量・バックアップと復旧・費用
