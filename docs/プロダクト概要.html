project-skeleton

AI と仕事を始める初日から、置き場・記録・仕組みが揃っている。

開発でも、PM でも、運用保守でも、インフラや SaaS の管理でも、同じ一式を使います。人が見るものはシンプルに、AI が読むものは詳細に。業務ごとに型を選び分ける必要はありません。タスク管理・最低限の記録・AI への指示（ハーネス）を最初から置いておき、使いながら自分たちのやり方に合わせて直していく。AI 導入の初動を早くするための起爆剤です。

# Claude Code に「○○のプロジェクトを作って」と頼むと、new-project skill がこれを実行する $ python3 scripts/init.py 新案件 --name "新案件" --slug new-case → タスク一覧の初期化 → git init + 初回コミット → 構成の検査まで一気に通す # 既存のフォルダには --merge。足りないファイルを足し、手を入れていないものは新しい版にする # 新しい版が出ると、作業フォルダを開いたときに Claude が気づいて更新を提案する
解決する課題

AI を入れても、仕事の型が整うまでに時間がかかる

AI を業務に入れるとき、最初につまずくのは AI の性能より、周りの整え方です。

何から整えるか決まらないタスクの置き場、記録の残し方、AI への指示。毎回ゼロから考え、手が止まる。
会話が流れて残らないAI とのやり取りで決まったことが、チャットに埋もれて翌日には探せない。
AI への指示が育たない同じ注意を何度も繰り返し、人ごとに指示がばらつく。うまくいったやり方が仕組みにならない。
3 つの起爆剤

最初に置いてあるのは、どの仕事にも要る 3 つ

機械は hook・スクリプト・検査で自動的に効くもの、手順は Claude Code が skill として読んで実行するものです。

01

タスク管理

Markdown 1 枚が 1 件。作業（タスク）と、まだ決まっていないこと（課題）を同じ置き場で持ち、一覧は HTML で切り替えて見ます。起票も完了も Claude Code に頼めば済みます。

手順task　機械new.py・close.py・build.py

02

最低限の記録

打合せや作業の区切りで出た「決まったこと・決まっていないこと・あとでやること」を Claude が拾い、置き場へ落とします。1 つの事柄の正本は 1 か所だけで、決まったことは課題に書きます。出来事の時系列（作業ログ）は正本から自動で作るので、二重に書きません。

手順pickup　機械pickup_check・work_log・session_context

03

ハーネス設計

同じ手順を 2 回した、「それはしないで」と言われた。そうした場面を Claude が候補として台帳に書き、承認されたものだけを skill・hook・ルールとして定義します。AI への指示が、仕事をしながら育ちます。

手順harness　機械check_harness

使う場面

業務を選ばない。効くところが違うだけ

型を選び分ける必要はありません。同じ一式を置き、その仕事で要るところから使います。下は例です。

場面よく効くところ
開発タスクと課題の管理、変更に合わせた設計書の追随、テストや hook の整備
PM 業務打合せ記録と落ち先、「決めてほしいこと」と期日の一覧、関係者と判断権限の整理
運用保守定常作業と追加開発をタスクで一緒に持つ。手順は runbook に残し、同じ手順の 2 回目はハーネスの候補にする
インフラ・SaaS の管理環境の実値を Git 管理外の環境情報に集める。設定変更の経緯を記録に残し、してはいけない操作は許可設定で止める
強制しない、育てる

決まりは初期値。合わなければ変えてよい

ここにある決まりは、よくある失敗を防ぐための出発点で、使い方を押しつけるためのものではありません。自分たちの方針に合わなければ変えられますし、変え方もこの中に用意してあります。

機械が止めたり、やり直しを促したりするのは 3 つだけ。秘密を共有物に書いたとき、決めた置き場の外にファイルを作ったとき、拾ったものがどこにも落ちていないとき。空欄・未記入・未決の多さでは止めません。直す文書の候補や鮮度は、知らせるだけです。
厳しさを変えるフェーズは Sketch と Build の 2 段。情報を集めている間は Sketch で拾うだけ。外へ出し始めたら AI が Build に上げ、報告で 1 行伝える。
置き場を合わせる既存の仕組みが使う決まった場所は .claude/project.json に書けば、ガードが通す。コードは書き換えない。
仕組みを足す・外すharness スキルで候補を台帳に書き、承認して定義する。拾い直しの hook は CLAUDE_PICKUP=off で止められる。
文書は育てる設計書は概要 1 本で始める。ほかは要るときに候補を出し、承認を得て 1 本ずつ足す。未記入は止めない。
既存のフォルダにも--merge は足りないファイルを足し、手を入れていないものだけを新しい版にする。手を入れたものは混ぜるか、一覧で見せる。
直したものを返す決まりを案件に合わせて変えたら台帳に 1 行。ほかでも効くものは「返す」列に書けば、スケルトン側で集めて取り込める。

拾って落とす

  • pickup決まったこと・未決・あとでやることを、反映済・タスク・課題のどれかへ

  • work_log作業ログを正本から作り直す（直近 14 日と月ごと）
  • design_docs_reminderファイルを変えたら、一緒に直す文書の候補と、案件で決めた「保存したらすること」を示す
節目

まとめて点検する

  • audit-design-docs記録・タスク・実物と突き合わせて見直しリストを作る
  • docs_freshness / check_drops文書の鮮度と、落ち先の無い行を一覧にする
機能一覧

指示しなくても働くものが大半

AI に細かく指示できなくても使えることを目指しています。「利用者の操作」が「不要」のものは、何も言わなくても hook か Claude が自分で動きます。新は v1.5.0 で入れたものです。全機能の詳細（いつ動くか・担当ファイル）はリポジトリの docs/機能一覧.md にあります。

区分機能利用者の操作
生成作業フォルダを 1 コマンドで作る。一覧の初期化・git・検査まで通す名前を伝える
追従新スケルトンに新しい版が出たら、開いたときに知らせて更新を提案する不要
追従新手を入れていないファイルは自動で新しい版に。手を入れた仕組みは変更を残して混ぜる。前の中身は退避「はい」と答える
追従新版ごとの定型の移行は自動。判断が要る手順だけ Claude が読んで進める不要
追従新既存フォルダに入れたら、中の資料を読んで概要・現在地などの下書きを作る下書きを直す
タスク起票・完了・一覧。ID は自動、課題は決定と落ち先が無ければ閉じない不要
タスク新完了条件のチェック漏れを、閉じるときに知らせる不要
記録区切りで決まったこと・未決・あとでやることを拾って落とし、作業ログを作る不要
設計書変更に合わせて直す文書の候補と鮮度を知らせる。足す文書は候補を出す足すか答える
置き場決めた置き場の外への書き込みと、秘密の転記を止める不要
現在地開いたときにフェーズ・タスク・文書の状況を Claude に渡す。フェーズは Claude が切り替える不要
ハーネス繰り返しや「しないで」を候補として台帳に書く。定義は承認後承認する
ハーネス新あるファイルを保存したら決まったことを促す（案件で 1 組ずつ足せる）不要
検査作業フォルダとスケルトン自身の検査・テスト。版の遅れは知らせるだけ不要
生成されるもの

作業フォルダの中身

CLAUDE.md ＋ .claude/rules

守ること・セッション開始時の手順・読む文書の表。rules は作業領域・文書管理・秘密の 3 本。

.claude/skills（10 本）

work-placement ／ scratch ／ task ／ pickup ／ harness ／ update-overview ／ update-env-info ／ sync-design-docs ／ audit-design-docs ／ draft-from-existing

.claude/hooks（6 本）

開始時の現在地とスケルトンの版、置き場のガード、変更時の文書の候補と保存の促し、依頼文の手がかりの記録、区切りでの拾い直しと作業ログ。テスト付き。

docs/案件/

タスクと課題（決まったことの正本も課題）、打合せ記録、相手に確認したいこと、作業ログ（生成物）。

docs/プロジェクト概要.html

目的・思想・現在地・これからの 1 枚資料。タスクの件数や決めてほしいことは自動で反映。

docs/ハーネス台帳.md

AI への指示の候補と、承認して定義したものの一覧。

docs/設計書

最初は 01 概要だけ。02〜09 はテンプレートから 1 本ずつ足す。長い理由の記録（decisions）と手順書（runbook）。

.work/ ・ 環境情報.md

Git 管理外。作業領域（証跡・機密・一時・退避）と、URL・アカウントなど実値の正本。

scripts/ ・ .claude/project.json ・ skeleton.json

構成・落ち先・文書の鮮度の検査。案件ごとの違い（決まった置き場・入れ子のリポ・保存の促し）は project.json に書く。skeleton.json はどの版を入れたかの記録。

文書のテンプレート

概要 1 本で始め、要るときに 1 本ずつ足す

最初から 9 本を並べると、書かない文書が負担になります。概要だけで始め、ほかは必要になったときに AI が候補を出し、承認を得て足します。足すと、索引と「変えたら一緒に直す文書」の対応表にも行が入ります。

#文書何の正本か
01概要目的・範囲・成功条件・用語（最初からある）
02構成仕組みや対象の構成・データの流れ・環境
03関係者ロール・判断権限・確認の取り方
04原則迷ったときの決め方・方針の変遷
05セキュリティ守るもの・権限・AI にさせてはいけない操作
06品質と確認何を壊れたとみなすか・確かめ方
07変更と反映変更の流れ・反映・戻し
08利用者の運用業務の流れ・権限の付与・障害時の文面
09非機能と障害時目標・容量・復旧・費用

v1.5.0 で入れたもの

指示しなくても追従し、揃う

似たツール 23 件（テンプレート同期・仕様駆動・AI 向けスターターなど）を調べ、AI に明示的に指示できない人でも、何も言わずに働くものを選んで入れました。

記録とずれの検知どの版を入れたかを作業フォルダに残す。新しい版が出たら、開いたときに Claude が気づいて 1 行で提案する。
自動で追従手を入れていないファイルは新しい版に。手を入れた仕組みは変更を残して混ぜ、衝突したものだけ相談する。
移行は一部だけ自動どこでも同じ結果になる手順だけを自動にし、判断が要る手順は Claude が読んで案件に合わせる。
既存の資料から下書き既存フォルダに入れたら、中の資料を読んで概要・現在地・案件情報の下書きを作る。直すのは誤りだけ。
完了条件の知らせタスクの完了条件をチェックリストに。漏れがあれば閉じるときに知らせる（止めない）。
保存の促しあるファイルを保存したら決まったことを促す。案件で 1 組ずつ足せ、コードは書き換えない。
