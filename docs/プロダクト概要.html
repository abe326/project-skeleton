project-skeleton

新しい案件を、初日から「運用の型」が揃った状態で始める。

タスク管理・作業領域・概要資料・環境情報・設計書・Claude Code の指示と仕組みを、1 コマンドで同じ形に生成するスケルトンです。書いた決まりは hook と検査で機械的に効かせます。初日は拾うだけで済み、作業の中で出た決定・未決・あとでやることは、どれも置き場へ落ちるまで追いかけます。

# Claude Code に「○○のプロジェクトを作って」と頼むと、new-project skill がこれを実行する $ python3 scripts/init.py 新案件 --name "新案件" --slug new-case → build.py → git init + 初回コミット → check_skeleton.py まで一気に通す
解決する課題

案件ごとに手で揃えると、ばらつき、抜け、古びる

これまでの案件で確立した運用は、フォルダ構成・スクリプト・Claude Code の設定に散らばっていました。新しい案件のたびに前の案件から写すと、次の 3 つが起きます。

ばらつく案件ごとに置き場やタスクの書式が少しずつ違い、Claude Code も人も毎回読み解き直す。
抜けるhook やガードの写し忘れで、「書いてあるのに守られない」決まりが生まれる。
古びる設計書や概要資料が実装に追いつかず、読んだ人が事実と違うことを信じる。
強み

決まりを「書くだけ」で終わらせない

機械は hook・スクリプト・検査で自動的に効くもの、手順は Claude Code が skill として読んで実行するものです。

1 コマンドで、毎回同じ形

生成・タスク一覧の初期化・git の初回コミット・構成の検査までを 1 回で通します。既存フォルダには --merge で足りないファイルだけを追加し、既存ファイルには触れません。案件ごとの違いは .claude/project.json に書き、テンプレのコードは書き換えずに済みます。

機械init.py ／ 外部依存なし

置き場の決まりを hook が止める

一時ファイルは .work/一時/日付_用途/ にだけ置く決まりです。ルート直下や .work/ 直下への書き込みは、書く前に hook が止めます。

機械PreToolUse の work_area_guard

セッション開始時に現在地を渡す

毎セッションの最初に、open タスクの件数・概要資料の最終更新日・要確認の設計書の本数を自動で注入します。Claude Code は読み回らずに現在地から始められます。

機械SessionStart の session_context

設計書が実装に置いていかれない

認証やスキーマなどを変えると、一緒に直すべき設計書を hook がその場で示します。直すときは「矛盾しないか」ではなく「この変更で何が決まったか」を 1 行拾い、決めずに仮置きしたものは課題にします。各設計書は鮮度の情報を持ち、未記入・期限切れ・対象ソースの変更を分けて知らせます。

機械design_docs_reminder・docs_freshness　手順sync-design-docs・audit-design-docs

影響の対応表は 1 つだけ

「変えたもの → 一緒に直す文書」の表を設計書の索引に 1 つだけ持ちます。hook・検査・skill が同じ表を読むので、仕組みごとに対応がずれません。表で書きにくい判定は差し込み口のコードに書けますが、そのときも表に 1 行を置き、入口は表のままにします。

機械impact_map.py が表を直接読む

秘密と共有物を分ける

URL・ID・パスワードは Git 管理外の 環境情報.md と .env にだけ書きます。Git に載る文書にパスワードらしき値・資格情報入りの URL・既知のトークン形式があれば、検査が値を出さずに指摘します。

機械check_skeleton.py の秘密検出　手順update-env-info

何も落とさない

作業中に出た決定・未決・あとでやることは、必ず「反映済・タスク・未決」のどれかに落とします。打合せ記録の各行に落ち先を書き、未決の正本は課題に一本化しました。落ちていないものがあるときだけ、ターンの終わりに 1 回だけ拾い直させます。

機械pickup_cue・pickup_check・check_drops　手順pickup

初日は拾うだけ、ハーネスは後から育てる

フェーズ(立ち上げ・開発・運用)で厳しさが変わり、立ち上げ期は設計書が未記入のままでも止めません。ハーネスは最初から固めず、作業中に生まれた候補を台帳に書き、承認されたものだけを定義します。

機械phase.py・check_harness　手順harness

1 日の流れで効く仕組み

機械(hook・スクリプト)手順(skill)
セッション開始

現在地を受け取る

  • session_contextフェーズ・open タスク・設計書の要確認と未記入・拾いもの・マシン側の混入を 8 行以内で注入
  • CLAUDE.md §7作業の種類に応じて読む設計書を絞る
作業の前

置き場を決める

  • work-placement紐づくタスクを確定してから手を動かす
  • scratch一時的な出力は日付フォルダへ
  • work_area_guard決まりに反する置き場は書く前に止める
変更したとき

その場で追随する

  • design_docs_reminder影響する設計書の候補を 1 回だけ示す
  • sync-design-docsソースを読んでから設計書と改訂履歴を直す
  • update-overview / update-env-info概要資料と環境情報も同じ作業で
  • pickup_checkターンの終わりに落ち先の無いものを見つけ、1 回だけ拾い直させる
節目

まとめて点検する

  • audit-design-docs打合せ・タスク・ソースと突き合わせて見直しリストを作る
  • docs_freshness / check_drops設計書の鮮度と、落ち先の無い行・ID の不在を一覧にする
生成されるもの

案件フォルダの中身

CLAUDE.md ＋ .claude/rules

絶対制約・セッション開始時の手順・読む設計書の表。rules は作業領域・文書管理・秘密の 3 本。先頭に生成元の版番号が入る。

.claude/skills(9 本)

work-placement ／ scratch ／ task ／ update-overview ／ update-env-info ／ sync-design-docs ／ audit-design-docs ／ pickup ／ harness

.claude/hooks(5 本)

SessionStart の文脈注入、PreToolUse の置き場ガード、PostToolUse の設計書追随、UserPromptSubmit の手がかり記録、Stop の拾い直し。テストケース付き。

.work/

Git 管理外の作業領域。証跡・機密・一時・_bk の 4 枠。

docs/案件/01_タスク管理

Markdown 1 枚 = 1 タスク。起票・クローズ・画面管理のスクリプトと、一覧を切り替えて見る index.html。

docs/プロジェクト概要.html

目的・思想・現在地・将来対応・構成図の 1 枚資料。マーカーで部分更新し、タスク件数は自動で反映。

docs/設計書

01〜09 の 9 本に、判断の記録(decisions)と手順書(runbook)。索引と影響マップは README に。

環境情報.md ／ 案件情報.md

URL・ユーザー・関係者・日程の正本。どちらも Git 管理外。

scripts/

構成を検査する check_skeleton.py と、設計書の鮮度を出す docs_freshness.py。
